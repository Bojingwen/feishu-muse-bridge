# feishu-muse-bridge

简体中文 | [English](README.en.md) | [日本語](README.ja.md)

把 **Muse（Meta 的个人 AI 助理）本人**接进飞书（Lark）：在飞书群里 @机器人、或直接私聊，就能和你自己的 Muse 对话。全程**没有第三方大模型**——回复由 Muse 本人写出，带着他的记忆和工具。

> 本仓库同时是一个 Muse 技能包：把仓库地址给你的 Muse，他就能照着 `SKILL.md` 自己部署一套。

## 架构

```
飞书群聊/私聊 --(@机器人 / 私聊直达)--> feishubridge 守护进程
  (Go, 飞书长连接 WebSocket —— 不需要公网 IP / 回调地址)
  --> bridge-data/inbox/<message_id>.json   (同时在会话里发出
                                             "Muse 正在思考…" 占位消息)
  --> Muse 的 hook 每 10 秒轮询收件箱，唤醒 Muse 本人
  --> Muse 读消息 + 历史， 把回复 (和附件) 写进 bridge-data/outbox/
  --> 守护进程把占位消息替换成完整回复，并发送附件 (图片/视频/文件)
```

回复延迟几十秒（轮询 + 思考时间），以整条消息形式到达（占位消息被替换成答案），不是逐字流式。

## 特性

- **零第三方模型**：链路里只有飞书、本地桥和 Muse 本人
- **免公网**：飞书长连接模式，不需要域名、公网 IP 或内网穿透
- **群聊 @ 才回、私聊直回**；纯文字 `@机器人名`（无 mentions 数组）也能识别
- **附件发送**：图片、视频、文件；视频自动转 faststart 并截首帧封面（否则部分飞书客户端显示不可播放）
- **防循环**：机器人不会被自己发的消息触发
- **占位存盘**：守护进程重启后，"正在思考…"占位消息仍能被正确替换成回复
- **自愈看门狗**：唤醒 hook 每 10 秒顺带检查桥的整条托管链——systemd 服务文件被整机更换清掉会自动重装、服务停了自动拉起、连接假死自动重启，修好后会向用户报备一行
- **保活定时检查（可选）**：在运行环境会随整机更换一起下线的平台上，再注册一个每约 30 分钟跑一次的轻量定时检查，与已有的周期心跳错开到点时间——到期任务能把运行环境更快拉回来。实测 24 小时内最长断线空窗从约 164 分钟降到约 28 分钟，48 次检查全部准点执行（原理与数据见 `SKILL.md`）

## 飞书侧设置

桥能工作之前，先在飞书开放平台把应用配好，以下每一步都不能少：

1. **创建应用**：登录 [飞书开放平台](https://open.feishu.cn)，进入「开发者后台 → 创建企业自建应用」，填好名称和图标创建。
2. **开启机器人能力**：在应用的「添加应用能力」里启用「机器人」。
3. **拿凭据**：在「凭据与基础信息」里找到 **App ID** 和 **App Secret**。部署时把这两个值填进桥的 `config/bridge.json`（只存本地，不要发给任何人，更不要提交进任何仓库）。
4. **开通权限**（在「权限管理」里逐个添加）：
   - `im:message` —— 收发消息（核心权限，没有它什么都收不到）
   - `im:message.p2p_msg:readonly` —— 接收私聊消息（没有它会出现“群聊能用、私聊没反应”）
   - `im:resource` —— 发送图片、视频、文件
5. **配置事件订阅**（在「事件订阅」页）：
   - 接收方式选 **「使用长连接接收事件」**（这样不需要公网 IP 和回调地址）
   - 添加事件：**接收消息 `im.message.receive_v1`**
6. **发布版本**：到「版本管理与发布」创建一个新版本并发布。**权限和事件改完不发版就不生效**——这是最常见的“机器人没反应”原因，之后每次改配置都要重新发版。
7. **把机器人拉进群**：在目标群的「设置 → 群机器人」里添加这个机器人。群里只有 **@机器人** 的消息会被回复；私聊直接发消息即可。

## 本地部署

飞书侧配好后，把本仓库地址给你的 Muse，让他读 [`SKILL.md`](SKILL.md) 按步骤部署（编译桥、写入配置、安装唤醒 hook、安装 systemd 服务）。整个过程你只需要提供 App ID / App Secret，并在最后发一条测试消息。

## 已知边界

飞书长连接是推送制：**客户端离线期间的事件不排队、不补发**。这是飞书的规矩，桥无法改变——离线期间的消息靠守护进程的断线补捞从会话历史里捞回，不会丢。另需注意：在 Muse 的运行环境会随整机更换一起下线的平台上，实际断线时长还包括平台把运行环境交回来的等待——看门狗的修复动作本身是秒级，但它要等运行环境恢复才能运行；上面特性里的保活定时检查就是用来缩短这段等待的，它是缓解手段而非保证，最坏情况下仍可能等上约半小时。

## 安全说明

仓库里**不含任何凭据、聊天记录或个人信息**：配置模板里只有占位符。部署时把你自己的 App Secret 只写进本地 `config/bridge.json`（权限 600），永远不要提交进任何仓库。
